## Store comparison and identity

The Qdrant branch supplied semantic results; the Elasticsearch branch supplied
BM25 results hydrated from PostgreSQL. In the A01/A02 running code, the
Elasticsearch Catalog hits had a real `title` but no `procedure_name` or
`thu_tuc`. Core read only the latter fields and rejected those hits as having
an empty procedure name. A focused read-only PostgreSQL/ES query confirmed
the payload shape. Working-tree code now falls back to the actual `title`,
with regression coverage. **That fix is not yet loaded in the live Core.**

The sampled same Healthcare upload point exists in both stores with identical
text and canonical Evidence ID, but Qdrant stores `record_id` inside
`record_fields`, while PostgreSQL hydration exposes it at the top level.
Working-tree RRF identity now reads either location. A Tourism live trace
showed two candidate pairs actually merged by RRF; branch point IDs, raw
scores and ranks remain in provenance. This is not a cross-store equality
audit of all records.

The Qdrant Healthcare collection still has 209 points: 100 Healthcare,
100 Education and 9 README rows, all tagged `healthcare`. Elasticsearch has
100 Healthcare and 100 Education records. The sampled Elasticsearch Education
record has `domain_id=education` but an Evidence ID beginning
`domain:healthcare:`; both current Evidence Builder and the working-tree
fusion guard reject this inconsistent identity. Qdrant and PostgreSQL/ES
were left untouched. These records require a separately reviewed data repair.

Legacy legal Qdrant points lack `domain_id` and source/document IDs, and
the Registry points `legal_ai` and `administrative_law` to the same vector
collection. Domain isolation for those vectors remains collection/policy
dependent. No human-approved relevance labels were available, so no
Qdrant-only versus ES-only versus Hybrid quality score is claimed. A full
runtime comparison would require additional controlled reloads because
`SEARCH_BACKEND` is process configuration. No live backend outage was induced;
the one-branch fallback is unit-tested only.

## Code and validation

Changed during this validation: the launcher no longer defaults to Hybrid;
`backend/search/hybrid.py` normalizes nested record IDs and rejects uploaded
Evidence IDs that conflict with their domain/document; `backend/rag/adapter.py`
retains retrieval provenance in Evidence metadata; `backend/search/candidate.py`
and `backend/main.py` read real Catalog titles; regression tests were added.
No threshold, model, LoRA, database record or collection was changed.

Full backend suite after these changes: **496 passed, one existing
Starlette/AnyIO deprecation warning**. This verifies the working tree, while
the running Core still uses the code loaded before the final title fix.

## Recommendation and remaining work

Do not make Hybrid the default yet. It is selectable explicitly, and a live
request did traverse the intended path. A01/A02 still failed citation
integrity, A03 and Tourism yielded no Evidence, Education provenance is
inconsistent, and the Catalog title fix needs another controlled reload to
validate. Keep `qdrant` as the launcher/Core default. After a reviewed data
repair and live verification of the title fix, compare modes on identical
human-labeled queries before assessing retrieval quality or latency gains.

The experimental live Core currently reports `hybrid`. Returning the live
stack to `qdrant`, or loading the final title fix into Hybrid, requires a
**second** full launcher reload because the launcher supervises all three
APIs. That reload was not performed under the one-reload authorization for
this run.
